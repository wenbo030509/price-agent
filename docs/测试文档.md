## 一、目录结构

```

    test_trace.py            ← L1/L2 TraceEvent + SSE 流式（72 用例）
    test_color_memory.py     ← 颜色/内存字段回归
    test_embedding.py        ← Embedding 客户端连通性（6 用例）
    test_m1_config.py        ← M1 行业配置框架（8 用例）

    test_m3_rag.py           ← M3 RAG 知识库（6 用例）

    test_query_fix.py        ← 查询修复回归

    eval_helpers.py          ← 公共模块：EvalRecorder / 评分 / 幻觉检测
    eval_p0_unit.py          ← P0 单元测试（无 LLM）
    eval_p1_parse.py         ← P1 属性解析（需 LLM）
    eval_p2_e2e.py           ← P2 端到端（需 LLM）
    eval_p3_boundary.py      ← P3 能力边界（需 LLM）
    eval_p4_benchmark.py     ← P4 回归基准（需 LLM）

    eval_p6_image.py         ← P6 图片搜索（需 LLM）
    eval_it3c.py             ← IT3C 手机品类综合评估
    results/                 ← 自动生成的 JSON 报告（gitignored）
```

## 二、两种测试的区别

| | tests/ | eval/ |
|------|--------|------|
| 用途 | 开发期模块验证 | 回归 + CI + JSON 报告 |
| 执行者 | 开发者手动跑 | 自动化 / 定时跑 |
| 输出 | 终端 pass/fail | JSON 报告，可追踪趋势 |
| LLM 依赖 | 部分 | P1-P6 全部 |
| 运行速度 | 快（秒级） | 慢（分钟级，P2+ 需 LLM） |

## 三、运行方式

### 开发期 — 跑单个模块

```bash
# pytest 运行（推荐）
python3 -m pytest tests/test_m1_config.py -v
python3 -m pytest tests/test_m2_recall.py -v
python3 -m pytest tests/test_m3_rag.py -v
python3 -m pytest tests/test_m5_shopping.py -v
python3 -m pytest tests/test_trace.py -v
python3 -m pytest tests/test_react_engine.py -v

# 或直接 python 运行
python3 tests/test_embedding.py
```

### 回归 — 跑评估套件

```bash
# P0 单元测试（无 LLM，秒级）
python3 eval/eval_p0_unit.py
python3 eval/eval_it3c.py          # IT3C P0, 50 case

# P1-P6（需 LLM，分钟级）
python3 eval/eval_p1_parse.py
python3 eval/eval_p2_e2e.py
python3 eval/eval_it3c.py --all    # IT3C 全部（含 P1/P2）
```

### 全量回归

```bash
# pytest 一键运行全部（推荐）
python3 -m pytest tests/ -v

# 或按模块单独运行
python3 -m pytest tests/test_trace.py -v
python3 -m pytest tests/test_react_engine.py -v
python3 -m pytest tests/test_m1_config.py -v
python3 -m pytest tests/test_m2_recall.py -v
python3 -m pytest tests/test_m3_rag.py -v
python3 -m pytest tests/test_m5_shopping.py -v

# 评估框架 P0
python3 eval/eval_it3c.py
python3 eval/eval_p0_unit.py
```

## 四、测试策略

### 什么时候跑什么

| 场景 | 跑什么 |
|------|--------|
| 改了一个模块 | 对应的 `tests/test_m*.py` |
| 改了一个工具 | 对应的 `tests/test_m*.py` + `eval/eval_p0_unit.py` |
| 改 Agent 路由 | `tests/test_m5_shopping.py` + `tests/test_react_engine.py` + `eval/eval_it3c.py` |
| 改 embedding | `tests/test_embedding.py` + `tests/test_m2_recall.py` |
| 改可视化 | `tests/test_trace.py`（72 用例，mock LLM） |
| 新增模块 | 写新的 `tests/test_m*.py` + 更新 `eval/eval_it3c.py` |
| 发版前 | 全量 `tests/` + `eval/` P0 |
| CI | `eval/` P0（无 LLM）+ `tests/` 全部 |

### 为什么不把所有测试放 eval 框架

1. **速度**：独立测试脚本秒级完成，eval 框架有框架开销
2. **独立性**：每个模块的验证逻辑差异大（配置/召回/RAG/购物），独立脚本更直观
3. **调试便利**：独立脚本可以直接 `python3 -i` 进入交互模式调试
4. **避免耦合**：eval 框架改 API 不影响独立测试，反之亦然

### 测试什么时候集合到 eval

当某个模块的测试满足以下条件时，才应该加入 eval 框架：
- 测试逻辑稳定，不再频繁修改
- 需要生成 JSON 报告追踪变化趋势
- 会被其他模块的修改影响，需要在回归中检测

M2 和 M5 已满足这些条件，已加入 `eval/eval_it3c.py`（VR-IT-01~05、SI-IT-01~10）。
